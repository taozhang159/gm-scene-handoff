# 场景配对与重复双向合并依据

## 动态配对

在固定开发提交、目标提交及必要历史版本中递归枚举 Assets/GMScenes/Test（含 Chapter_XX 子目录）。按文件名 TestScene_all_NNN.unity 与 TestScene_all_NNN_<作者>.unity 配对，不固定 001/002/003，支持 004 和后续三位编号。作者从实际开发分支/指定交付源识别，不使用操作者用户名，不固定 zhangtao；解析不唯一时询问。

可运行技能工具 `handoff.py scenes --project <项目> --author <实际作者> --refs <开发SHA> <目标SHA>`，只读列出各版本的场景对、缺失及重复状态。只有一侧存在时记录缺少个人/基础场景；没有个人场景仍需检查直接基础修改和公共依赖。多个目录同编号不得任选；移动通过 .meta GUID 和历史追溯，重建同名个人场景必须视为新的开发世代。

首次复制场景后单独提交有助于定位起点，但不是强制前提。没有历史记录时从创建/复制提交、内容相等性和修改历史重建；merge-base 仅是线索。无法证明共同起点时仅暂停该场景的写入，继续可确定的只读准备。

## 三方语义

统一采用 A（共同基准）、S（输入侧）、T（接收侧），结果 R 将 A→S 应用到 T。保留接收场景身份。必须固定普通 Git 合并前场景内容，结合 Git 已应用的变化核对，不从合并后的文件倒推原 T。

sync 的 R 只写当前作者个人场景；deliver 的 R 只写目标基础场景。场景文件的保护与 Git 索引处理见 [执行流程](merge-workflow.md)。当前分支基础场景在 sync 后保持旧内容，因此不是“已接收的主分支版本”，也不能在后续 deliver 中被当作应覆盖目标的最新基础。Git 合并祖先可能已前移而受保护文件没有更新，必须分别追踪代码合并历史和场景接收历史。

| 方向与情况 | A 的首选依据 | S | T |
|---|---|---|---|
| 首次 sync | 个人场景复制时的基础场景 | 最新主分支基础场景 | 当前个人场景 |
| 再次 sync | 上次有效 sync 已接收的主分支基础版本 | 最新主分支基础场景 | 当前个人场景 |
| 首次 deliver，尚未 sync | 个人场景复制起点 | 当前个人场景 | 最新目标基础场景 |
| 再次 deliver | 上次有效 deliver 已接收的个人场景版本 | 当前个人场景 | 最新目标基础场景 |

该表不是无条件选取算法。交替双向操作时还要重放两个方向的有效记录：

- 首次 deliver 前已 sync：同步时的基础 S 可成为当前个人场景已吸收的基准，须检查 sync 冲突决定、个人场景后续修改，以及当前目标包含该版本。
- deliver 后再 sync：将上次已交付个人 S 及基础结果 R 的对应关系纳入判断。不能把本人的已交付修改误认为主分支的新改动而重复应用；可把该个人 S 作为与交付结果共同关联的比较锚点，核对后续源、目标变化。
- sync 后再次 deliver：个人场景中来自主分支的新增变化与目标已有变化需对齐、去重；以前明确排除或选择不同侧的字段须保留决定，新修改则重新裁决。
- 候选锚点无法表达删除、重建、冲突选择等历史时，不强行简化成一个提交号；结合前后双方快照逐项建立映射，不能用整场景覆盖。

例：个人 A0 交付成基础 M1，个人继续改为 A1、主分支继续改为 M2。再次 deliver 比较 A0→A1 并保留 M1→M2；反向 sync 也需利用 A0↔M1 的已接收关系，不能仍从最初复制点重放。目标前移、源 rebase/重建、分支改名均要核实历史和 GUID；不能只比较作者或时间。记录不足可从 Git 恢复，存在歧义再询问。

没有新变化时为已对齐，不重复加对象、不制造空提交；Git already up to date 不证明两个不同文件间已迁移。删除/重挂/字段冲突按当前真实差异处理，记录不能成为覆盖对方修改的授权。

### 多轮执行的判断

| 执行顺序 | 下一轮的比较与预期 |
|---|---|
| sync → sync | 以上次有效 sync 的基础 S 为已接收锚点，只迁移后来主分支变化，保留个人在上次 R 之后的编辑；当前分支基础文件仍不写入 |
| deliver → deliver | 以上次有效 deliver 的个人 S 为已交付锚点，只交付后来个人变化，保留目标基础在上次 R 之后的编辑；旧开发基础中的过时值不构成回滚依据 |
| sync → deliver | 用 sync 的 S↔R 关系识别个人场景已吸收的主分支内容，与目标基础去重，再交付个人独有及后续增量 |
| deliver → sync | 用 deliver 的 S↔R 关系识别本人已交付内容，只吸收基础后来变化并保留个人后续修改，不能把本人旧交付当作新的主分支增量 |
| sync → deliver → sync → deliver | 串联同一场景世代的双向有效记录，逐项继承接收关系和冲突决定；每轮仍只写方向对应目标 |
| 任意方向原样重跑 | S 未变化不意味着覆盖 T；保留 T 后续编辑，已处理的源增量不再执行。内容和记录均已对齐时无场景写入、无空提交 |

记录的是“哪些源变化已处理，以及当时如何处理”，不要求 R 与 S 完全相等。源值未变而接收侧后来调整时保留接收侧；源再次修改同一字段时，以双方自各自已记录快照以来的变化重新判断。历史明确排除或选择目标值也属于已处理决定，不能因结果不同于源值而反复提议覆盖。单个 A 无法表达此关系时，保留成对前后快照并逐字段比较，不强造共同基准。

## 可跨机器的记录

每轮 `Docs/SceneHandoffs/<本轮目录>/scene-sync.json` 保存 schema_version、operation_id、direction（sync/deliver）、author、development_branch、project_path、source_commit、target_before_commit、previous_records 和 scenes。每个场景包含编号、基础/个人路径及 GUID、开发世代/复制起点依据、A/S/T 的 commit/path/blob，R 的 path/SHA-256，以及冲突、排除和验证状态。

新记录增加 `scene_write_policy: directional-v1`、`scene_write_allowlist` 和 `protected_scenes`。白名单包含允许写入的场景及 `.meta` 项目相对路径；保护项保存接收起点的路径、存在性、commit/blob 及结果核对状态，覆盖源侧新增、删除和移动涉及的路径。每对场景另记录直接基础修改的来源快照、逐项处理决定及引用的前次 operation_id；deliver 的 target_before_commit 指完成远程对齐、尚未合入开发提交的目标。新结构提升 schema_version；旧记录保持原样，缺少新字段不推断为已验证保护策略，但经内容核实的旧 S↔R 仍可用于重建接收关系。

用项目相对路径、Git 提交/blob 和结果内容哈希定位，不能依赖绝对盘符、聊天或某台机器的 .git 状态。记录随结果提交，不为了写入自身结果提交号循环提交；下次从包含该记录的 Git 提交及其树确认结果路径/哈希和祖先关系。祖先关系不足以证明内容，仍需核对记录与实际 blob。原记录保留，后续事件引用它。

只有结果已提交、相关冲突已解决且源/结果均可追溯的记录可作为成功同步依据；验证状态独立记录，人工未验不得标为通过。pending、失败、被取消、仅有候选文件的记录不能推进成功基准。不能选择时间最新但属于另一作者/场景/世代的记录。

场景路径/GUID/复制世代用于身份，分支名用于辅助检索；主程从待交付开发分支读 sync 记录，从目标历史读 deliver 记录。新一轮从 develop_base 建分支并复制新个人场景时重新识别起点，不继承上一轮个人场景锚点。旧记录未拉取时正常追溯 Git，不要求同事手动初始化数据库。

## 验收场景

修改此规则或未来通用迁移器时，至少审查：首次同步/交付；源再次修改；目标再次修改；重复执行无变化；上述各项多轮顺序；双方改同字段；删除与修改；直接基础修改与个人修改重叠；主程操作他人分支；004/后续编号和子目录；缺失/重复配对；记录丢失、换电脑及新开发世代。另核对 sync 基础字节不变、deliver 个人字节或不存在状态不变、无冲突/快进候选/已合并三种 Git 状态均不能绕过保护、源侧场景移动和新增不泄漏到非目标路径。当前工具只发现配对，不自动证明基准、执行路径保护或替代 Unity 场景语义合并；这些检查由执行流程完成。
